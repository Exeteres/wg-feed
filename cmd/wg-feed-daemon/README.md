# wg-feed-daemon

wg-feed-daemon is a long-running wg-feed client.

It continuously syncs enabled feeds (SSE or polling) and reconciles local managed tunnels for all configured backends per feed.

## Usage

Default config lookup path:

- `/etc/wg-feed/config.yaml`
- `/etc/wg-feed/config.yml`
- `/etc/wg-feed/config.toml`
- `/etc/wg-feed/config.json`

Run with default lookup:

```sh
wg-feed-daemon
```

Run with explicit config path:

```sh
wg-feed-daemon --config ./config.yaml
```

## Config format

Minimal example:

```yaml
state_path: /var/lib/wg-feed/state.json

feeds:
  main:
    sync:
      enabled: true
      mode: sse
      polling:
        interval: 0
      endpoints:
        - https://example.invalid/sub#agekey
    backends:
      default:
        type: wg-quick
    tunnels:
      demo-primary:
        enabled: true
```

Important behavior:

- `sync.enabled=false` skips the feed entirely.
- `sync.mode=sse` tries SSE and falls back to polling when unsupported.
- `sync.mode=polling` uses polling only.
- `sync.polling.interval > 0` forces fixed polling period.
- `sync.polling.interval = 0` uses server `ttl_seconds`.
- Endpoints are the input URLs for feed sync.
- One feed can target multiple backends (for example `wg-quick` + `networkmanager`, or `netns`).
- `tunnels.<tunnel_id>.enabled` is an optional feed-wide override.
- `backends.<backend_label>.tunnels.<tunnel_id>.enabled` is an optional backend-scoped override.
- Effective enabled precedence is: backend-scoped override > feed-wide override > feed document `tunnels[].enabled`.
- Server `forced` is ignored for enable/disable decisions.
- `netns` backend creates a per-tunnel Linux network namespace and moves the tunnel interface into it.
- `netns` namespace names match calculated device names and are persisted in tunnel state for stable re-apply/remove.

Environment expansion:

- Any string value in config supports `$VAR` / `${VAR}`.
- Unset env vars are a hard config load error.

## Encrypted feeds (age)

For encrypted responses, add the age key fragment to feed endpoints (`https://...#<fragment>`).

All endpoint fragments for one feed must represent the same key.

## State file format

Top-level shape:

```json
{
  "state_id": "<uuid-v4>",
  "feeds": {
    "<feed_label>": {
      "id": "<remote_feed_id>",
      "last_reconciled_revision": "<revision>",
      "ttl_seconds": 3600,
      "cached_encrypted_data": "-----BEGIN AGE ENCRYPTED FILE-----\n...",
      "endpoint_order": ["<hmac_sha256(canonical_endpoint_url_no_fragment)>", "..."],
      "backends": {
        "<backend_label>": {
          "type": "wg-quick",
          "tunnels": {
            "<tunnel_id>": {
              "data": {
                "device_name": "wg0"
              }
            }
          }
        }
      }
    }
  }
}
```

Notes:

- `state_id` is generated by client state loading and used as installation-scoped key material for endpoint hash derivation.
- `feeds` is keyed by configured feed label.
- `id` is the remote feed document id discovered at runtime.
- `endpoint_order` stores salted endpoint hashes (no cleartext endpoint persistence).
- `cached_encrypted_data` is persisted only for encrypted responses.
- `backends` stores tunnel state independently per configured backend label.
- `tunnels[*].data` is backend-specific JSON payload.

## Running in containers

wg-feed-daemon is a long-running process and works well as either:

- A host-level service container (Linux host network), or
- A Kubernetes sidecar in the same Pod network namespace.

### Docker (host network)

Run daemon in the host network namespace (Linux):

```sh
docker run --rm \
  --network host \
  --cap-add NET_ADMIN \
  -v /etc/wg-feed/config.yaml:/etc/wg-feed/config.yaml:ro \
  -v /var/lib/wg-feed:/var/lib/wg-feed \
  ghcr.io/exeteres/wg-feed/daemon:latest
```

### Docker Compose (sidecar-style)

You can share daemon network namespace with another service:

```yaml
services:
  wg:
    image: ghcr.io/exeteres/wg-feed/daemon:latest
    network_mode: host
    cap_add: ["NET_ADMIN"]
    volumes:
      - /etc/wg-feed/config.yaml:/etc/wg-feed/config.yaml:ro
      - /var/lib/wg-feed:/var/lib/wg-feed

  app:
    image: your-app:latest
    network_mode: "service:wg"
    depends_on: [wg]
```

### Kubernetes (sidecar in a Pod)

Run wg-feed-daemon alongside an application container in the same Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-wg
spec:
  volumes:
    - name: wgfeed-state
      emptyDir: {}
    - name: wgfeed-config
      secret:
        secretName: wg-feed-config

  containers:
    - name: wg-feed-daemon
      image: ghcr.io/exeteres/wg-feed/daemon:latest
      securityContext:
        capabilities:
          add: ["NET_ADMIN"]
      args:
        - --config
        - /etc/wg-feed/config.yaml
      volumeMounts:
        - name: wgfeed-state
          mountPath: /var/lib/wg-feed
        - name: wgfeed-config
          mountPath: /etc/wg-feed
          readOnly: true

    - name: app
      image: your-app:latest
```

Notes:

- You may need additional cluster/node configuration if WireGuard kernel support is unavailable.
- Treat config files and endpoint URLs as secrets.
